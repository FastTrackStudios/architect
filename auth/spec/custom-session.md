# Custom session

r[auth.custom-session.typed-hook]
Custom session enrichment MUST use a typed hook that receives the normal
session bundle and returns a service-defined custom payload type.

r[auth.custom-session.backcompat]
Custom session support MUST preserve the normal user, session, and raw
token fields so existing session callers can keep using the standard
`AuthSessionBundle` behavior.

r[auth.custom-session.axum]
Axum integration MUST expose custom session data through a typed request
extension so handlers can access the service-defined payload type without
unsafe downcasting.

r[auth.custom-session.vox]
Vox integration MUST expose custom session data through a typed request
extension so RPC handlers can access the service-defined payload type
without unsafe downcasting.

r[auth.custom-session.openapi]
OpenAPI metadata MUST represent custom session responses as a generic
schema extension over the stable session envelope until service-specific
schemas are generated by Architect metadata.

r[auth.custom-session.serialization]
Custom session serialization MUST be backwards compatible: unknown custom
fields are additive, and clients that only understand the stable session
envelope can ignore the custom payload.

r[auth.custom-session.plugin-descriptor]
The custom-session capability MUST be represented by an Architect auth
plugin descriptor with a stable id, upstream parity target, dependencies,
and capability names.

r[auth.custom-session.plugin-routes]
The custom-session plugin descriptor MUST own custom-session route
metadata used by transport and OpenAPI adapters.
